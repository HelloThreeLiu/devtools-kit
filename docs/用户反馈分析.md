## 1. 分析方法

逐条归类 → 同一诉求去重合并（计数）→ 与本插件现有实现逐项比对 → 给出处置结论：

- ✅ **已覆盖**：现有功能已有解法（验证产品方向，个别引出小改进）
- 🔍 **质量自查**：竞品踩坑场景，检查我们是否有同类隐患
- 🚀 **纳入排期**：下一期功能候选，分 P0 / P1 / P2
- ❌ **明确不做**：原理不可行或平台不符，附理由

优先级综合三个因素：**反馈热度**（提及条数）、**定位契合度**（纯本地、开发者高频）、**实现成本**。

## 4. 🚀 下一期功能候选

### 4.1 P0 —— 强烈建议纳入 v1.1

#### F1. 图片/文件 ↔ Base64 互转（反馈 8 条，热度第一）

- **诉求明细**：webp 不支持 ×2、svg 不支持 ×1、Base64 显示图片 ×1、解码后复制图片 ×1、还原结果保存文件 ×1、任意文件转 Base64 ×2、图片转 Base64 结果错误 ×1
- **方案**：将 PRD 4.3.8（P2 预留位）提前落地
  - 编码方向：选择/拖入任意文件 → 输出 Base64 与 Data URL（MIME 按扩展名推断：png/jpg/jpeg/gif/webp/svg/bmp/ico，未知类型按 `application/octet-stream`）
  - 解码方向：粘贴 Data URL 或裸 Base64 → 识别图片 MIME → 预览 + 复制图片（`utools.copyImage`）+ 另存为
  - svg 属文本格式，按 Data URL 正常处理；webp Chromium 原生支持渲染（竞品翻车点，对我们零成本）
- **技术要点**：preload 侧 `node:fs` 读文件；大文件（> 10 MB）给进度或体积警告
- **工作量**：M（新工具页 + preload 桥接 + MIME 推断单测）

#### F2. 字符编码转换：GBK / UTF-8 / UTF-16LE / UTF-16BE 双向（反馈 3 条）

- **诉求明细**：缺 GBK ×1、四件套 Encode/Decode ×1、Unicode 工具里加 GBK ×1
- **场景**：日常开发中文乱码排查刚需（用户原话：「少了很多猜乱码的环节」）
- **方案**：升级 Unicode 工具为「字符编码转换」（或新增工具）
  - 解码：Chromium `TextDecoder` 原生支持 `gbk` / `utf-16le` / `utf-16be`，**零依赖**（2026-11-26 已实测）
  - 编码：UTF-16LE/BE 经 preload `Buffer` 零依赖；GBK 编码无原生 API，需自建映射表或评估 `iconv-lite` 体积
- **差异化可选项**（后置）：输入乱码文本 → 猜测原始编码
- **工作量**：M–L（GBK 编码表是主要成本）

#### F3. Base64 健壮性增强（反馈 4 条间接相关）

- 解码前剥离**全部**空白字符（空格/换行/Tab）——当前仅 `trim()` 首尾，PEM、邮件折叠排版会误报「包含非法字符」（对应反馈「换行符过滤」×1）
- 显式 **Base64URL 输出**开关（`-`/`_` 字符集、去 padding）（对应反馈 ×1）
- 解码失败时错误提示追加「尝试宽容模式」引导（对应「解码经常没有输出」×3 的根源性改善：竞品静默失败，我们必须显式报错 + 给出路）
- **工作量**：S（纯函数改动 + 单测）

### 4.2 P1 —— 建议 v1.1 ~ v1.2

#### F4. UUID 增强：v7 + ULID（反馈 2 条）

- **UUIDv7**（RFC 9562，时间有序、索引友好，后端趋势明确）；**ULID** 批量生成（可加 Monotonic 选项）
- 顺带保证单条结果双击复制不含换行（竞品被坑 ×1，见 §4.4-3）
- 工作量 S–M，纯函数可单测（v7 = 48bit 毫秒时间戳 + 随机位，构造规则明确）

#### F5. 文件哈希 + 多文件对比（反馈 5 条）

- **诉求明细**：多文件 MD5 ×1、只算指定算法 ×1、大文件进度显示 ×1、多文件哈希对比 ×1、Linux SHA1 修复 ×1
- **方案**：哈希工具增加「文件模式」
  - preload 流式读取分块 `crypto.createHash`（2G 文件不爆内存）
  - 算法**勾选**（默认可只算 MD5，避免全算一遍太慢）
  - 进度条（百分比 + 当前文件名）
  - 多文件列表：高亮相同/不同，支持「找出重复文件」
  - 入口：文件拖入 + 超级面板评估（见 F15）
- **工作量**：L（含 UI 与三平台真机走查）

#### F6. 进制转换增强：Hex ↔ 文本、小数支持（反馈 4 条）

- **Hex ↔ 字符串**（×2）：UTF-8 编解码，hex 展示格式可选（连续 / 空格分隔 / `0x` 前缀）
- **小数进制转换**（×2，含「不能输入小数点」）：整数部分除基取余 + 小数部分乘基取整，精度上限建议 52 位（IEEE 754 双精度尾数），超出提示截断
- 工作量 M

#### F7. 哈希计算增强（反馈 3 条）

- MD5 **16 位输出**（取标准 32 位的第 8–24 字符）×1
- 可选 **salt**（前/后拼接并标注规则）×1
- 「生成随机字符串并求哈希」按钮 ×1（测试数据场景）
- 工作量 S

### 4.4 🔍 顺带修复的小项（分析中的发现）

1. **时间戳入口正则放宽**：`public/plugin.json` 现为 `^\d{10,13}$`，9 位秒级时间戳（2001-09 之前）粘贴不会自动呼出工具。建议放宽至 8–13 位，方向判断交给工具内数量级阈值兜底（对应反馈「9 位时间戳识别不对」×2）
2. **URL 解码宽容模式**：`decodeURIComponent('中文20%英文')` 因孤立 `%` 整体抛错——竞品因此被吐槽 ×2，**我们实测同样存在**。建议非法 `%` 序列按字面保留、其余正常解码，并标注「部分内容无法解码」
3. **复制内容统一 trim**：保证任何工具复制到剪贴板的内容无首尾空白/换行（对应「UUID 复制带隐形回车」×1）
