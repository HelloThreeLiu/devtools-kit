## 1. 规划原则

1. **热度优先**：反馈条数多的需求优先（图片/文件 Base64 ×8 条为热度第一）；
2. **产品决策优先级高于观察池**：明确指令的需求（本版新增的加密模块、Cron 等）按指定排期落地；
3. **快赢先行**：小改动高价值的修复包放第一个迭代首周，快速响应反馈；
4. **承诺不破**：所有新功能坚持纯本地计算，不引入网络请求；新增运行时依赖必须先做体积评估（PRD §5 包体积 ≤ 10 MB 约束）；
5. **依赖现状**：preload 已具备 `node:crypto` 与 `node:fs` 桥接（2026-11-26 核实），加密与文件类需求无需新增底座，按「最小暴露原则」新增业务动作即可；
6. **缓冲预留**：每版本排期含 15–30% 缓冲，应对审核与突发修复；
7. **可降级标注**：单项需求标注 ★可裁剪，进度吃紧时降级到下一版本，不影响版本主题完整性。

**工作量口径**：S = 1–2 人日，M = 3–5 人日，L = 6–10 人日（含单测与文档，不含审核等待）；产能按每周 5 人日计。

### 3.3 需求详情与验收要点

#### R1.1 快赢修复包

1. **时间戳入口正则放宽**：`public/plugin.json` 的 `^\d{10,13}$` → `^\d{8,13}$`，方向判断交由工具内数量级阈值兜底；同步更新 `scripts/check-match-regex.mjs` 用例（对应反馈「9 位时间戳识别不对」×2）。
2. **URL 解码宽容模式**：`decodeUrl` 遇非法 `%` 序列不再整体失败——非法片段按字面保留、其余正常解码，返回值增加 `partial` 标注，UI 显示「部分内容无法解码」（对应反馈「中文20%英文」×2，本插件实测同样存在）。
3. **复制内容统一 trim**：`src/utils/clipboard.js` 的 `copyText` 对入参统一 `String(text).trim()`，杜绝首尾空白/换行进入剪贴板（对应反馈「UUID 复制带隐形回车」×1）；UUID 工具单条复制路径同步核查。
4. **URL 智能模式**（产品决策，对应竞品「http 开头全编码/非 http 部分编码」语义）：输入以 `http(s)://` 开头时自动采用 `encodeURI`（保留 URL 结构），否则 `encodeURIComponent`（全编码）；仍保留手动双模式切换与完整 URL 结构化解析。

**验收**：`中文20%英文` 宽容解码输出原文并带 partial 标注；9 位秒级时间戳粘贴可呼出工具；任一工具复制结果无首尾空白；`https://a.com/?kw=你好` 智能模式仅编码参数值部分；原有 163 个单测零回归。

#### R1.2 Base64 健壮性增强（`src/utils/convert/base64.js`）

- 解码前剥离**全部**空白字符（空格/换行/Tab），支持 PEM、邮件折叠排版（当前仅 `trim()` 首尾）；
- 新增 Base64URL 编码输出开关（`+ /` → `- _`、去 padding），与既有 URL-Safe 解码容错形成双向闭环；
- 解码失败错误文案追加「可尝试去除空白后重试」引导。

**验收**：含换行的合法 Base64 解码成功；`hello` → Base64URL `aGVsbG8` 往返一致；竞品失败案例（`eyJ0eXBl…` 无 padding）保持可解；新增用例进 `tests/base64.spec.js`。

#### R1.6 JSON 转义 / 去转义（并入现有 JSON 工具）

- **转义**：任意文本 → JSON 字符串字面量（`他说:"hi"` → `"他说:\"hi\""`），可选是否保留外层引号；在「格式化 / 压缩」旁新增操作按钮；
- **去转义**：转义串 → 原文；容错接受带/不带外层引号；非严格 JSON 转义时按 `\n \t \r \" \\ \/ \b \f \uXXXX` 规则手工还原；
- 纯函数扩展进 `src/utils/convert/jsonFormat.js` 并补单测。

**验收**：中英混排 + 引号 + 换行文本转义→还原往返一致；`\"\\u4f60\"` 类输入可还原「你」；含非法转义序列时报错并给出位置原因。

#### R1.7 Base32 编解码（新工具，编解码分类）

- RFC 4648 标准（字母表 A–Z + 2–7，补位符 `=`）；UTF-8 安全（TextEncoder / fatal TextDecoder）；支持带/不带 padding 的解码容错；方向自动识别可后置；
- 注册 `plugin.json` feature（cmds 建议：`base32`）；纯函数进 `utils/convert/base32.js`。

**验收**：RFC 4648 官方向量通过（`hello` → `NBSWY3DP`）；中文「你好」编码→解码往返一致；无 padding 输入可解码；非法字符报错含原因。

#### R1.4 字符编码转换（新工具，编解码分类）

- **定位**：专注 GBK / UTF-8 / UTF-16LE / UTF-16BE 四编码 × Encode/Decode 矩阵；既有 Unicode 工具保持专管 `\uXXXX` 转义序列，职责不混。
- **解码**：`TextDecoder('gbk' | 'utf-16le' | 'utf-16be')`（Chromium/Node 原生支持，零依赖，2026-11-26 已实测）；支持带/无 BOM。
- **编码**：UTF-16LE/BE 经 preload `Buffer`（零依赖）；GBK 编码按 SPIKE-1 结论落地（依赖表或 iconv-lite，见 §7）。
- **输入输出**：文本 → 目标编码字节（hex / Base64 两种展示）；字节 → 文本；注册 feature（cmds 建议：`编码转换` `GBK` `乱码`）。

**验收**：「你好」GBK 编码 `C4E3 BAC3` 且可解码还原（v1.3 勘误：原文 `C4E3 BAD6` 实测为「褐」，系笔误）；UTF-16BE/LE 各含 BOM 用例正确；乱码样例（GBK 字节按 UTF-8 打开后）可经本工具复原；纯函数单测齐全。

> v1.5 勘误（2026-11-28 实测）：「GBK 字节按 UTF-8 打开」方向一般**不可复原**——GBK 双字节大量组合（如 C4E3 的 E3）不是合法 UTF-8 序列，按 UTF-8 解码已产生 U+FFFD 丢失信息；可复原的是反方向：**UTF-8 字节被按 GBK 打开**（如 浣犲ソ ↔ 你好，每对字节恰为合法 GBK 码位）。本工具两条路径均支持（文本↔字节矩阵 + 乱码复原样例进单测），验收以可逆方向为准。

#### R1.5 图片/文件 ↔ Base64 互转（新工具，编解码分类，反馈热度第一）

- **编码方向**：`<input type="file">` + 拖拽上传任意文件 → 输出 Base64 与 Data URL；MIME 按扩展名推断（png/jpg/jpeg/gif/webp/svg/bmp/ico，未知按 `application/octet-stream`）；> 10 MB 给体积警告。
- **解码方向**：粘贴 Data URL 或裸 Base64 → MIME 识别（`data:` 前缀解析；裸 Base64 做魔数嗅探：PNG/JPG/GIF/WEBP(RIFF)/BMP/ICO，SVG 按文本特征 `<svg`/`<?xml` 识别）→ 图片预览 + 复制图片（`utools.copyImage`，API 入参形态开发期真机验证）+ 另存为（`utools.showSaveDialog` + preload 新增保存动作）★可裁剪。
- **说明**：webp/svg 无需特殊支持——DataURL 按正确 MIME 渲染即可（竞品翻车点，对我们零成本）。

**验收**：png/jpg/webp/svg/gif 五类样本编码→解码→预览往返一致；裸 Base64 无 MIME 信息时可凭魔数正确识别；竞品全部相关反馈场景（webp ×2、svg、显示图片、复制图片、保存文件、任意文件 ×2）逐条可演示；MIME 推断表纯函数单测。

### 4.3 需求详情与验收要点

#### R1.3 哈希计算增强（`src/utils/convert/` + `src/tools/hash/`）

- MD5 16 位输出（取标准 32 位的第 8–24 字符）；
- 可选 salt：前缀/后缀两种拼接模式，UI 明示拼接规则；
- 「生成随机字符串」按钮（`crypto.getRandomValues`，16/32 位可选）生成后自动计算哈希。

**验收**：MD5-16 与第三方工具一致；`abc` + salt 前缀/后缀结果可手工复算；随机字符串每次点击不同且熵源为 crypto API。

#### R1.8 JWT 解码（新工具，编解码分类）

- 三段式（`header.payload.signature`）与两段式容错；header/payload Base64URL 解码 → JSON 格式化展示 + 声明表格；signature 段原样展示并标注「未验证」；
- 时间声明 `exp` / `iat` / `nbf` 自动转本地时间并标注「已过期 / 有效」；
- 明确提示：首版仅解码不验签（验签需密钥，HMAC 验签列入后续评估）；复用 Base64URL 解码逻辑，零依赖。

**验收**：竞品失败案例（`eyJ0eXBl…`）完整解码展示；构造含过期 `exp` 的 JWT 正确标注；非法段数/非法 Base64 报错含原因；payload 为 JSON 时格式化展示。

#### R2.7 Cron 表达式解析（新工具，时间日期分类）

- 支持标准 5 段（分 时 日 月 周）与 Quartz 6/7 段（秒 分 时 日 月 周 [年]），按段数自动识别；
- 输出：逐字段解析表格（值 / 范围 / 步进 / 列表 / 通配）、中文描述、未来 5 次触发时间（本地时区）；
- 语义约定：默认 Vixie cron 语义（日与周同时受限取 OR）；提供 Quartz 模式切换（取 AND）；`L` / `W` / `#` 特殊字符首版仅支持常用子集并在界面列明支持范围；
- 纯 JS 自研解析器，不引入依赖。

**验收**：`0 9 * * 1-5` → 「工作日 09:00」+ 未来 5 次正确；`*/15 * * * *` 步进正确；Quartz `0 0 12 ? * MON-FRI` 可解析；与 crontab.guru / Linux crontab 对拍 ≥ 20 用例；非法表达式报错并指出字段位置。

#### R2.5 AES 加解密（新工具「AES 加解密」，编解码分类）

- **生成密钥**：`crypto.randomBytes`，长度 128 / 192 / 256 位可选，输出 hex / Base64；
- **加密**：模式 CBC（默认，PKCS7）与 GCM（推荐）；IV 自动生成并随输出返回（分栏展示，不与密文混写）；输出 Base64 / Hex 可选；
- **解密**：对应模式反向；GCM 校验失败报「密文或密钥不匹配」；
- 密钥 / IV 支持粘贴 hex 或 Base64；preload 按「最小暴露原则」新增业务动作；纯本地，密钥不存储。

**验收**：AES-128-CBC 结果与 OpenSSL 命令互验（`openssl enc -aes-128-cbc -K … -iv …`）；GCM 篡改密文解密报错；错误密钥解密给友好提示不崩溃；密钥生成随机性抽查。

#### R2.1 UUID 增强

- **UUIDv7**（RFC 9562）：48bit 毫秒时间戳 + ver 7 + rand_a 12bit + variant + rand_b 62bit；
- **ULID**：48bit 时间戳 + 80bit 随机数，Crockford Base32；同毫秒内提供 Monotonic 递增选项；
- 版本选择 UI（v4 / v7 / ULID），批量 1–100 与格式切换沿用现状；新增 cmds（`ulid`）。

**验收**：v7 时间戳字段与生成时刻一致（±1ms）、版本/变体位校验通过；ULID 长度 26、字母表合法；Monotonic 同毫秒严格递增；批量 100 个唯一；纯函数单测（注入固定时间/随机源）。

#### R2.2 进制转换增强

- **Hex ↔ 文本**：UTF-8 字节与 hex 双向；hex 输入容忍空格/逗号/`0x` 前缀；输出格式可选（连续/空格分隔/`0x` 前缀）；
- **小数进制**：2/8/10/16 进制均支持小数点；整数部分除基取余 + 小数部分乘基取整，精度上限 52 位（IEEE 754 双精度尾数），超出提示截断位置。

**验收**：`19.625` ↔ 二进制 `10011.101` 双向精确；`E4BDA0E5A5BD` → 「你好」；非法 hex（奇数长度等）报错含原因；循环小数场景给出截断提示；用例进 `tests/radix.spec.js`。

### 5.3 需求详情与验收要点

#### R2.8 RSA 加密模块（新工具「RSA 加解密」，编解码分类）

- **生成密钥对**：`crypto.generateKeyPairSync('rsa')`，2048 / 4096 位可选，公钥 SPKI PEM、私钥 PKCS#8 PEM，展示 + 复制 + 下载；4096 生成耗时秒级，放 preload 异步 + loading 提示，默认 2048；
- **基于私钥生成公钥**：`crypto.createPublicKey(privateKeyPem)` → 导出 SPKI PEM（与 openssl `rsa -pubout` 等价）；
- **公钥操作**：加密（OAEP 默认 / PKCS#1 v1.5 可选）、验签（SHA-256 / SHA-1）；
- **私钥操作**：解密、签名（输出 Base64）；
- 粘贴任意 PEM 均先做格式校验（BEGIN/END 包裹 + base64 体），报错给出具体原因。

**验收**：生成的密钥对可用 `openssl rsa -in priv.pem -pubout` 互验；OAEP 加解密往返一致；签名/验签正反例通过（篡改内容验签失败）；私钥提取的公钥与 openssl 产物一致；非法 PEM 报错不崩溃。

#### R2.4 文件哈希 + 多文件对比

- preload 新增 `hashFile(filePath, algos, onProgress)`：`fs.createReadStream` 分块流式 `crypto.createHash`，多算法一次遍历（勾选控制）；
- UI：文件列表（拖入/选择，多选）+ 算法勾选（默认仅 MD5，可展开全选）+ 进度条（百分比 + 当前文件名 + 已算/总量）+ 结果对比高亮（相同/不同分组，一键筛出重复文件）；
- 入口：工具页选择文件；若 SPIKE-2 结论可行，同步接入超级面板文件入口；
- 三平台（尤其 Linux）真机走查，对应竞品「Linux SHA1 失败」事故。

**验收**：2 GB 级文件哈希不爆内存、进度实时；与 `certutil` / `shasum` 结果一致；多文件对比分组正确；取消/重算可用；Windows/macOS/Linux 三平台通过。

#### R2.3 ASCII 码表/互转

- 字符 ↔ 码点（十进制/十六进制）双向；输入序列输出对照表；内置 0–127 可查询全表。

**验收**：`A` ↔ 65/0x41；混合文本对照表逐字符正确；控制字符显示助记名（如 NUL/ESC）。

## 7. 技术准备（Spike 与决策点）

| 编号 | 事项 | 时间 | 备选方案 | 决策标准 |
| --- | --- | --- | --- | --- |
| SPIKE-1 | GBK **编码**实现路径（解码已确认零依赖） | W1 | a) `iconv-lite`：能力完整，需评估体积（dist ≤ 10 MB 约束）；b) 自建 GBK 常用区映射表（GB2312 全部 6763 汉字 + 常用符号）；c) v1.1 先交付 GBK 解码 + UTF-16 双向，GBK 编码移入 v1.2 | 体积增量 > 1 MB 则倾向 b/c；结论与体积数据记录于此并更新 §10 状态 |
| SPIKE-2 | uTools 超级面板能力验证 | W2 | plugin.json 超板配置（文件入口/文本入口）真机验证 | 验证匹配行为、与现有 regex feature 的冲突情况；结论决定 R2.4 入口与 F15 立项 |

**SPIKE-1 结论**（2026-11-28，实测验证，编码侧不降级）：

- **解码方向**：`TextDecoder('gbk')` 零依赖可用（Node 24 与 Chromium 同源 WHATWG 码表），`fatal: true` 可校验非法字节，已实测通过；
- **编码方向**：采纳**新增方案 d——运行时构建逆向映射表**：遍历 GBK 双字节区间（lead `0x81–0xFE` × trail `0x40–0xFE` 去除 `0x7F`），对每个码位用 `TextDecoder('gbk', { fatal: true })` 反解，得到「字符 → 字节」完整映射，惰性构建、模块级缓存；
- **实测数据**（Node 24.13）：构建耗时 8.8 ms；收录 21,791 字符（未分配码位与 PUA 用户定义区自动排除）；`你好` → `C4 E3 BA C3`；中英混排往返一致；
- **备选对比**：a) iconv-lite@0.7.3 未打包 344 KB（低于 1 MB 门槛，保留为兜底）；b) 静态映射表体积可控但覆盖不全、需人工维护；**方案 d 零依赖、零打包体积增量，码表与平台解码器天然一致（往返必然成立），且 vitest/Node 可直接单测**；
- **边界**：GBK 表外字符（Emoji、GB18030 四字节区等）编码时逐字符报出「不支持的字符」，UI 明示；渲染进程需支持 `TextDecoder('gbk')`（uTools 为 Chromium，与 Node 同表，已核实）；
- **勘误**：§3.3 R1.4 验收样例「你好」GBK 字节应为 `C4E3 BAC3`（原文 `C4E3 BAD6` 实测解码为「褐」），已同步修正。

**SPIKE-2 准备**（2026-11-28，配置草案与验证清单就绪，**待 uTools 真机验证**）：

候选配置（暂不入正式 plugin.json，避免未验证配置进入提审产物；真机通过后再合入）：

```json
{
  "code": "encoding",
  "explain": "字符编码转换 / 乱码复原",
  "cmds": [{ "type": "over", "label": "编码转换" }]
}
```

真机验证清单（结论回填本节，决定 R2.4 入口与 F15 立项）：

1. 选中文本 → 超级面板是否展示该 feature；`onPluginEnter` 收到的 `payload` 形态（文本内容 / 对象结构）；
2. 选中文件 → 是否展示；`payload` 是否为文件路径数组（决定 R2.4 文件哈希入口写法）；
3. 与现有 regex feature（时间戳 / URL / JSON / UUID / 颜色）的匹配优先级与冲突情况；
4. `code` 分发是否符合现有 `toolByCode` 路由（超板 feature 需在 `tools/index.js` 注册或在 router 层特殊分发）。

**既有基础确认**（2026-11-26）：

- `public/preload.js` 已引入 `node:crypto`（createHash）与 `node:fs`，按「最小暴露原则」新增 `readFileAsBase64`、`saveFile`、`hashFile`、AES/RSA 系列业务动作即可，无底座性改动；
- AES/RSA 全部能力由 `node:crypto` 原生提供，**零新增运行时依赖**；
- JWT 解码、Base32、JSON 转义/去转义、Cron 解析均纯 JS 可实现，**零新增运行时依赖**；
- 「Hash 加密」即现有哈希工具（单向不可逆；MD5-16 / salt / 随机串增强见 R1.3）；MD5「解密」原理不可行，维持不做（用户反馈分析 §6）。
